# Contributing to Super Converter

Thanks for helping. Bug reports, files that don't convert well, feature ideas, documentation and code are all welcome.
This page covers the dev setup, how the project is laid out, the conventions the code follows, the self-tests, the
quality bench and the renders, and how releases are made.

## Dev setup

You need macOS 14 or later and the Swift toolchain from the Command Line Tools (`xcode-select --install`). Xcode is
optional; there's no Xcode project.

```sh
git clone https://github.com/udsy19/super-converter.git && cd super-converter
scripts/fetch-vendor.sh          # the pinned vendor libraries into Vendor/ (checked against Vendor.lock)
scripts/tools.sh fetch           # the bundled LGPL FFmpeg, ffprobe and 7-Zip into Vendor/Tools (Tools.lock)
scripts/signing-setup.sh         # once: a project-local signing identity in .signing/, so permissions survive rebuilds
scripts/build-app.sh --debug     # → build/Super Converter.app, with its static launch checks
open "build/Super Converter.app"
```

`swift build` alone compiles everything (including the self-tests, the bench and `sconv`) without making an app
bundle. `swift run sconv <files…> --to jpg` converts from the command line. Never put Homebrew's FFmpeg in `Vendor/`:
it's a GPL build.

## Project layout

                             sconv, the self-tests and the bench

                             is written by scripts/gen-format-matrix.py), option profiles, intermediate models,
                             Services, Defaults, Strings, design tokens
  ImageKit/ VectorKit/ XPSKit/ VectorizeKit/ CADKit/ DocKit/ TypesetKit/ MathKit/ LayoutKit/ RenderKit/
  OfficeKit/ EbookKit/ ArchiveKit/ MediaKit/ FontKit/

  HelperKit/                 helper catalog runtime, detection, one-click installs, the sandboxed process runner
  UpdateKit/                 background updates from GitHub Releases
  ConvertKit/                converter registry, planner, job queue, output rules, sniffer, thumbnails, PDF routes,
                             the sconv command
  WindowKit/ MenuBarKit/ SettingsKit/   the window, the menu-bar panel with Quick Actions and Services, Settings
  SuperConverter/            app target: launch, wiring, menus, Dock, Open With, links, the updater
  SuperConverterQuickActions/  the Finder Quick Action extensions (one executable, six plists)
  sconv/                     the command line's entry point
  SuperConverterSelfTest/    headless checks: one file per module, plus the fuzz cases
  SuperConverterQualityBench/  the quality bench: cases per kit, metrics, harness, report
Resources/                   Info.plist (written from the catalog), entitlements, fonts, hyphenation, MathJax
Tests/                       the bench's corpus and goldens (Tests/README.md)
scripts/                     build-app, make-dmg, release, signing-setup, make-icon, vendor and tool builds, fixtures,
                             gen-format-matrix

[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) explains how the modules fit together (§3–§4), the planner (§6), helpers
and packaging (§7) and the launch sequence (§9). Read §4's rules before your first change.

## Conventions

- **Engines depend only on `SuperConverterCore`** and their vendor libraries, plus the few engine-to-engine edges
  ARCHITECTURE §4 lists (TypesetKit → MathKit, VectorKit; EbookKit → DocKit, TypesetKit; …). The self-test checks the
  import graph. Feature modules talk through the `Services` registry; only ConvertKit imports engines.
- **Intermediate models live in Core** as plain `Sendable` data. A change to a model or a contract updates every
  reader, writer and fake in the same change.
- **Routes are data.** What converts to what is `docs/specs/data/format-matrix.json`, generated by
  `python3 -I scripts/gen-format-matrix.py` together with Core's `Catalog/Generated/` Swift. Don't edit either by hand.
  The planner only follows routes the matrix lists, and `App.everyRouteHasAConverter` fails if a route names an engine
  no converter registers, or a converter is registered that no route uses.
- **Engines carry no app policy**: no `Services`, no `Defaults`, no UI strings except `ConversionError` messages.
  Configuration comes through initialisers.
- **Processes run only through HelperKit's runner** (scrubbed environment, sandbox, time limit). Never `Process`
  anywhere else.
- **Licences.** No GPL or AGPL code is linked, loaded or ported. Ports of permissive code carry a provenance comment
  (`// Adapted from <repo> <path> (commit <sha>)`, formats §2.6) and a section in `THIRD_PARTY_NOTICES.md`.
- **Everything is local** unless ux §6.6 and [PRIVACY.md](PRIVACY.md) list it. Anything new that touches the network
  gets its own switch, stays off by default unless the app depends on it, and is documented in PRIVACY.md.
- **No dead code.** When you replace or remove behaviour, delete the old implementation, its helpers and its tests in
  the same change. No placeholders, no commented-out blocks.
- **Copy** follows ux §7: sentence case, curly quotes around names, a real ellipsis on anything that opens something,
  verbs with counts on buttons, no exclamation marks. Comments cite the spec section they implement (`quality §2.3`).
- **Design tokens** come from `SuperConverterCore/Design` (ux §3). Don't put literal sizes or colours in views.
- `swift build` must be **warning-free**.

## Self-tests, the bench and renders

The Command Line Tools ship no XCTest, so tests are an executable with a small `check(_:_:)` harness:

```sh
swift run SuperConverterSelfTest
SUPERCONVERTER_SELFTEST_ONLY=Core.,ImageKit.jpeg swift run SuperConverterSelfTest   # only cases with these prefixes
```

Each module registers its cases in `Sources/SuperConverterSelfTest/<Module>Tests.swift`. Cases use the throwaway
Application Support folder and defaults suite the harness sets up, never touch the network unless they say so (and
skip cleanly offline), and never open, launch or activate another app or a URL: inject a fake opener. The
`<Kit>.damagedInputNeverCrashes` cases fuzz every in-process reader with damaged copies of its fixtures
(`SUPERCONVERTER_FUZZ_SEED` reruns with another seed). Add cases for any new logic.

The quality bench measures what [quality.md](docs/specs/quality.md) promises (ΔE2000, SSIM, PSNR, loudness, LaTeX
parity, round trips…):

```sh
swift run SuperConverterQualityBench                 # the fast tier, as CI runs it
swift run SuperConverterQualityBench --tier full     # everything; some cases need helpers or scripts/fetch-corpus.sh
swift run SuperConverterQualityBench --only <case>   # one case; --list lists them, --bless <case> rewrites its golden
```

The report is `.build/quality/index.html`. How to add fixtures and cases for a kit: [Tests/README.md](Tests/README.md).
A PR that blesses a golden says why.

Offscreen renders of the real UI, for checking the look and for the screenshots in the README and USAGE.md:

```sh
SUPERCONVERTER_RENDER_DIR=/tmp/renders SUPERCONVERTER_SELFTEST_ONLY=WindowKit.renders,MenuBarKit.panelRender,SettingsKit.rendersEveryPane \
  swift run SuperConverterSelfTest
```

writes PNGs of the window (empty, dragging, cards, the format picker, the options sheet, converting, done, the list;
light and dark), side-by-side comparisons with `docs/mockups/`, the menu-bar panel and every Settings pane in light
and dark. `WindowKit.renders` fails when a render drifts from its mockup. To refresh `docs/images/`, copy the renders
of the same names over it. `sh docs/mockups/render.sh` re-renders the mockups themselves (needs Google Chrome).

`SUPERCONVERTER_WRITE_PLISTS=1 swift run SuperConverterSelfTest` rewrites `Resources/Info.plist` (keeping its version
keys) and the Quick Actions' plists from the catalog; the self-test fails when they differ.

## Pull requests

1. One change per pull request, with a clear description of what it does and why. Link the issue if there is one.
2. `swift build` compiles without warnings, `swift run SuperConverterSelfTest` passes and the fast bench passes.
3. A conversion change comes with a bench case that would fail without it; a new engine or route keeps
   `App.everyRouteHasAConverter` green.
4. UI changes come with a render and follow `docs/specs/ux.md` and the mockups.
5. Behaviour changes update the spec they touch (`docs/specs/`) and, if users will notice, `docs/USAGE.md`, and get a
   line in CHANGELOG.md under *Unreleased*.
6. Network or data-handling changes update PRIVACY.md; a new dependency or port updates THIRD_PARTY_NOTICES.md.

The pull request template has this as a checklist.

## Reporting bugs

Use the [bug report template](https://github.com/udsy19/super-converter/issues/new/choose). It asks for your Super
Converter and macOS versions, your Mac, the conversion (from → to), which helpers are installed, steps to reproduce and
what you expected. Logs are in Console.app, filtered by `com.udsy.superconverter`. A sample file that shows the
problem helps most; please only attach files you're happy to make public. Security issues go through
[SECURITY.md](SECURITY.md), not the tracker.

## Releases

Maintainers only. Releases are built on the maintainer's Mac and published to GitHub Releases:

1. Move *Unreleased* in CHANGELOG.md into the version's `## [<version>]` section (the release notes come from it;
   `release.sh` refuses without one).
2. `scripts/release.sh <version>` sets the version and build number in `Resources/Info.plist`, commits, builds the
   universal DMG with `make-dmg.sh` (Developer ID signed and notarised when `DEVELOPER_ID` and `NOTARY_PROFILE` are
   set, otherwise signed with the project-local identity), tags `v<version>` and creates the GitHub release with
   `SuperConverter-<version>.dmg` and a stable `SuperConverter.dmg`, with the DMG's SHA-256 at the end of the notes.
3. Running copies pick the release up through UpdateKit, which checks that SHA-256 and that the new app is signed
   like the running one. The signing identity of the first public release must never change.

The website and the one-line installer (`scripts/install.sh`) are published from `website/` by
`.github/workflows/pages.yml`.
